# MVP 产品规格

- 状态：已确认，待样本与原型验证
- 所有者：项目维护者
- 最后核验：2026-07-25
- 事实来源：项目负责人要求；原设计报告中已接受的本地账本、去重和确认原则；ADR-0009

## 一句话定义

面向支付宝、微信支付和银行账户的本地优先 Android 个人财务聚合器：通知只尽力捕获可见即时事件，已验证的来源账单/对账单只补齐其实际覆盖的账户腿，统一账本负责确认、去重和资金语义。

## 目标

- `G-01` 核心账本、解析、查询、对账和导出离线可用，无自有服务端依赖。
- `G-02` 支付宝、微信支付和银行通过统一来源契约进入相同流水线。
- `G-03` 三类来源分别拥有即时/主动采集、历史补齐和手工回退的明确组合；不得用一个账户的证据虚构另一个账户的内部流水。
- `G-04` 将经济事件、支付渠道与实际资金账户分开表示。
- `G-05` 同一消费的多来源证据不会造成重复支出。
- `G-06` 原始证据、解析版本、规则、用户修改、关联和撤销可追溯。
- `G-07` 严格、混合、自动三种确认策略均可由用户理解和控制。
- `G-08` 正确管理资产、信用卡/贷款负债和投资持仓。
- `G-09` 提供版本化加密备份、恢复和用户可读导出。
- `G-10` 提供余额校验、未匹配工作台、期初余额和月结基础。

## 首期用户旅程

### 1. 首次设置

用户了解本地优先承诺，建立现金、主要银行账户/信用卡、支付宝余额、微信零钱和可选投资账户，填写期初余额；随后按来源启用已验证的采集能力或导入历史账单，并选择确认策略。无法采集的钱包余额内部流水必须显示为缺口，而不是由银行记录补写。

用户可以跳过任何授权。跳过后应用解释缺失能力，但手工录入和已有账本仍可用。

### 2. 即时消费

受支持来源通知到达后，系统只保存允许列表包产生的必要证据，生成草稿并提出经济类型、分类、渠道和资金账户建议。用户确认后原子过账。

通知属于 `Best effort`：它不能补历史，也可能被系统、OEM 或上游文案变化影响。

### 3. 历史导入与补齐

用户通过系统文件选择器或分享入口选择账单。系统先预览来源、格式、账户映射、新增/重复/异常数量；用户确认后再事务性提交。再次导入相同或重叠文件不会重复过账。

### 4. 跨来源关联

只有当支付宝/微信实际从绑定银行卡或信用卡直接扣款，且金额、时间和账户提示一致时，系统才建议把它们关联为同一经济事件。银行记录作为资金证据，不生成第二次支出；微信零钱/支付宝余额内部收付没有银行资金腿，不能这样关联。

### 5. 日常复核

草稿箱和对账工作台集中显示未知格式、疑似重复、转账对、还款、退款和余额差异。用户可以确认、修改、拆分、关联、驳回或撤销。

### 6. 负债与投资

信用卡消费形成负债，后续还款只在资产账户与负债账户间移动；基金/理财申购和赎回使用投资语义。首期投资以用户导入或手工持仓为主，不承诺自动抓持仓。

### 7. 备份与离开

用户可创建完整加密备份、验证恢复、导出可读表格并删除所有本地数据。应用不以云账号锁定用户。

## 范围内能力

- Android 原生单用户应用。
- 通知监听：支付宝、微信支付、按包名启用的银行 App；只在真实适配器/模板验证后启用，不能承担完整钱包余额保证。
- 账单导入：按当前设备/账户/地区实测可用的用户账单路径，以及经样本验证的银行结构化对账单映射器；公开说明不是已支持声明。
- 手工交易、期初余额、账户余额校验。
- `RawEvent -> Draft -> Transaction + Entries` 主流程。
- 支出、收入、转账、充值、退款、负债形成/还款、投资买卖、费用、调整。
- 重复、pending/posted、渠道资金来源、转账对、退款与还款关系。
- 草稿箱、确认面板、未匹配工作台、撤销与审计。
- 应用私有存储、最小权限、加密备份与完整导出。

## 非目标

- 不承诺 100% 自动或覆盖全部银行。
- 不读取其他 App 私有数据库，不抓取登录凭据，不绕过安全控制。
- 不把支付平台/银行商户 API 冒充个人账单 API。
- Play 主线不依赖短信箱、无障碍自动操作、悬浮窗、Root 或抓包。
- 不做 24 小时截屏、录屏或轮询 OCR。若未来采用无障碍读取，必须是用户明确授权的被动、事件驱动、只读采集；不得自动点击、发起交易或替用户导航。
- 不建设自有云同步服务；多设备同步另行决策。
- 不执行交易，不提供投顾、收益承诺或信用建议。
- 不优先做多人协作、社交、广告、游戏化和复杂预算系统。

## 发布验收

1. 三类来源各有至少一条由真实脱敏样本证明的可用采集/导入路径。
2. 每个宣称支持的具体格式有版本、样本、黄金回放、失败提示和支持状态。
3. 同一绑卡消费的支付渠道与银行证据端到端只形成一次支出。
4. 重复导入同一文件、同一通知重放和任务重试均幂等。
5. 正式交易分录平衡；转账、充值、还款和申赎不污染普通收支。
6. 未知通知或文件格式安全停在草稿/错误状态，不猜测过账。
7. 用户修正不会被低可信重导入覆盖，并可撤销自动关联/自动确认。
8. 无网络时完成手工、导入、确认、查询、对账、备份和恢复。
9. 权限撤销、进程重建、导入中断和恢复失败都有可验证的安全状态。
10. 生产日志、崩溃信息、仓库夹具和诊断包不含真实财务敏感数据。
11. 完整删除和备份恢复通过自动化测试。
12. 所有“Supported”声明与自动生成的实际支持矩阵一致。

## 尚待产品负责人选择、但不阻塞内核的事项

- 首批具体银行名单及借记卡/信用卡优先级。
- Play-only 还是同时提供独立内测/F-Droid/GitHub 构建。
- 投资是否在首期扩展到微信零钱通和银行理财。
- 多币种、拆分交易、部分退款和预算报表的首期深度。
- 原始通知保留期限、数据库静态加密威胁模型和备份恢复口令体验。
- 是否把“用户明确授权的、被动事件驱动无障碍读取”作为经合规审批的实验性钱包适配器；该决定不得默认开启。

在这些选择完成前，架构按可扩展契约实现，不对未验证机构作营销承诺。
