## 四层视图

1. **总账**：所有经确认经济事件与平衡分录。
2. **账户/渠道**：现金、银行、信用账户、电子钱包余额，以及作为元数据的支付渠道。
3. **负债**：信用卡、贷款等独立余额、账单日、到期日和还款节点。
4. **投资**：投资现金、标的、持仓批次、成本和可选市值。

净资产可以汇总展示，但负债不得被隐藏为资产的负数后失去独立到期信息。

## 账户类型

| 类型 | 含义 | 示例 |
| --- | --- | --- |
| `ASSET_CASH` | 现金 | 钱包现金 |
| `ASSET_BANK` | 银行资产账户 | 工资卡、储蓄卡 |
| `ASSET_EWALLET_BALANCE` | 真正持有余额的电子钱包 | 支付宝余额、微信零钱 |
| `ASSET_WRAPPER` | 仅表示支付渠道的虚拟包装层 | 支付宝渠道、微信支付渠道 |
| `LIABILITY_CC` | 信用卡负债 | 招商信用卡 |
| `LIABILITY_LOAN` | 贷款负债 | 消费贷、房贷 |
| `INVESTMENT_CASH` | 投资账户待投资现金 | 基金账户现金 |
| `INVESTMENT_SECURITY` | 证券/基金持仓容器 | 某基金持仓 |
| `EQUITY_ADJUSTMENT` | 期初与对账调整 | 期初权益 |

`ASSET_WRAPPER` 默认不参与净资产；如果渠道本身持有余额，应使用独立 `ASSET_EWALLET_BALANCE`。

同一平台在不同交易中可以是支付渠道，也可以是真实余额账户。只有资金实际从绑定的银行卡或信用卡扣划时，银行/信用卡记录才是该交易的资金腿；若资金从支付宝余额或微信零钱扣划，电子钱包余额本身才是资金账户。银行卡流水不能推导或补齐钱包余额内的消费、收款、红包、个人转账或退款。

## 经济类型

- `EXPENSE`、`INCOME`
- `TRANSFER`、`TOPUP`
- `REFUND`
- `LIABILITY_DRAW`、`LIABILITY_REPAY`
- `INVEST_BUY`、`INVEST_SELL`
- `FEE`、`ADJUSTMENT`

UI 使用用户语言展示这些语义，但持久层使用稳定枚举和版本化迁移。

## 典型记账结果

### 支付渠道绑借记卡消费 32 元

- 经济事件：`EXPENSE`
- 渠道：支付宝或微信（元数据）
- 资金账户：银行借记卡
- 分录：费用增加 32，银行资产减少 32
- 若有两份通知：建立 `FUNDED_BY`，不生成第二笔支出

### 信用卡消费 800 元，之后还款 800 元

消费：费用增加 800，信用卡负债增加 800。

还款：信用卡负债减少 800，银行资产减少 800；还款不再次增加费用。

### 银行转入微信零钱 2,000 元

若资金确实进入微信零钱：`TOPUP/TRANSFER`，微信零钱资产增加，银行资产减少；不计收入。

这条记录只证明跨账户充值，不能推导之后任何一笔零钱消费、红包或收款。

### 使用微信零钱余额消费 32 元

- 经济事件：`EXPENSE`
- 渠道：微信支付（元数据）
- 资金账户：微信零钱
- 分录：费用增加 32，微信零钱资产减少 32
- 银行没有对应扣款时，不存在可关联的银行资金腿。

### 红包与个人转账的状态

- 未领取红包、未接受转账、过期或原路退还且从未进入本人余额：不是本人已发生的资金流，不创建收入、退款或支出分录。
- 已领取/接受并进入钱包余额：必须先有钱包侧可验证证据，再由用户确认其是收入、代收、转账或其他语义。
- 先进入余额、后又单独转回：是两笔已发生的钱包资金移动，未来由显式关系关联；默认不能当作商户退款。

### 基金申购 500 元

`INVEST_BUY`：投资持仓/投资现金增加，银行或钱包资产减少；不计普通消费。

## 负债要求

- 保存债权人、账户、账单日、到期日、年化率（若用户提供）、最低/应还金额和状态。
- 还款必须关联来源资产账户和目标负债账户。
- 账单提醒不等同于真实交易；只有导入/确认的还款才过账。
- 提前还款、分期、利息和手续费分别建模，不以余额修正掩盖。

## 投资要求

- 当前 CNY 纵向切片支持手工创建持仓，或由用户主动选择一张截图在设备上 OCR 预填后逐项确认；名称和当前金额必填，基金代码、份额和成本可选。
- 当前金额是带 `asOf` 的用户确认估值快照，不是实时净值。OCR 只填空白字段，图片、URI 与识别原文不写入持仓；简体和繁体标签都必须兼容，英文/日文仅在显式字段标签下预填。
- 每个持仓对应独立 `INVESTMENT_SECURITY` 账户；创建时以平衡的期初调整纳入净资产。之后确认的 `INVEST_BUY` 只移动资金账户与该投资账户的资产，不计普通支出，也不自动改写原估值快照。
- 不从支付/银行通知猜测完整持仓；通知只能提出申购/赎回草稿。
- 投资通知不得自动创建持仓或推断标的；用户必须选择既有、已确认持仓和同币种资金账户。申请受理、收益或行情提醒不创建资金草稿。
- 支付宝基金、微信零钱通和银行理财均通过投资适配器扩展，不能写进统一账本核心。

## 余额与期间

- 期初余额继续由平衡 `ADJUSTMENT + Entries` 表示；用户还可为现金、银行卡、电子钱包余额和信用卡保存某一时点的不可变余额快照。投资与贷款不复用这条路径。
- 快照金额按用户视角输入为零或正数：资产表示实际余额，信用卡表示实际欠款。现金/钱包仅 CNY，银行卡/信用卡可为 CNY 或 USD；不做汇率换算。
- 系统只汇总 `ACTIVE` 且 `occurredAt <= snapshot.asOf` 的分录，并在比较前把信用卡内部负数转换为正数欠款；差异定义为“实际快照 - 同时点账本余额”。
- 差异为零显示已对上，非零显示带符号金额和待解释；保存快照不会创建收入、支出、转账、退款或调整。后来补录/撤销发生在快照之前的交易会重算差异，快照之后的交易不会污染历史比较。
- 钱包余额快照只说明账本有待解释差异，不能用银行卡流水、历史模式或差额自动补写钱包内部逐笔流水。
- 当前账户页只显示每账户最新快照，Room 保留全部历史；历史管理、解释工作台、用户预览后调整与月结期间仍是后续能力。
