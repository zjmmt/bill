# ADR-0008：来源证据租约暂存与孤儿回收

- 状态：已接受；Room v5 核心恢复切片已实现，发布级压力与系统进程强杀矩阵未完成
- 所有者：项目维护者
- 最后核验：2026-07-25
- 事实来源：当前 `source:review-contract`、`application`、`data:local` 与 Room v5 实现；ADR-0006、ADR-0007

## 背景

来源证据文件和 Room 不能组成同一个物理事务。旧流程先原子写入应用私有文件，再提交 RawEvent 与载荷生命周期；进程若在两者之间退出，会留下没有数据库索引的文件。ADR-0007 的 16 MiB/512 份预算只统计 Room 已知载荷，因此无法发现或约束这种孤儿，也不能在不知道是否仍有提交者时直接扫描删除。

## 决定

### 文件写入前登记租约

- Room v5 新增 `source_evidence_staging`。每个新分享先登记 `ACTIVE` 行，绑定 opaque payload ID、RawEvent ID、SHA-256、字节数、随机 lease ID、创建时间和到期时间；表中不保存原文。
- 默认活动租约为 5 分钟。相同请求可以用新的 lease ID 续租；ID、哈希或大小冲突失败关闭。正在由恢复任务持有且尚未到期的载荷返回用户可见的“恢复中，请稍后重试”。
- 只有活动登记成功后，才允许把证据写入 `noBackupFilesDir/source-evidence`。

### RawEvent 事务原子消费登记

- `SHARE_TEXT` RawEvent 必须存在完全匹配的活动登记。RawEvent、`source_evidence_payloads` 生命周期和登记删除在同一个 Room 事务中提交。
- 如果登记已被恢复任务接管、字段不一致或消费 CAS 失败，整个 RawEvent 事务回滚；不得出现“数据库声称证据可用，但文件所有权已经丢失”的部分成功。
- 重放已存在 RawEvent 时仍检查不可变字段和 `AVAILABLE` 生命周期。已清除载荷不能由旧 command 复活。

### 到期接管与有界扫描

- 启动维护和新分享前的维护最多接管 128 个到期租约。接管用 lease ID 与到期时间做 CAS，把行改为 `RECOVERY`；晚到的 RawEvent 提交因此失败，而不是与删除并行成功。
- 恢复者删除精确的 `.blob`、`.blob.new` 和 `.blob.bak` 后才删除 `RECOVERY` 行。删除失败保留恢复行，后续可重试。
- 为处理 v4 及更早版本已经存在但没有 journal 的文件，维护只扫描修改时间至少 10 分钟以前的条目；单轮最多检查 4096 个目录项、认领 512 个 payload。扫描先排除数据库已知的 `AVAILABLE`、`CLEAR_PENDING`、`ACTIVE` 和 `RECOVERY` payload，再为候选创建恢复行，最后删除文件。
- `CLEARED` 生命周期不再保护异常残留文件；它们可以被恢复任务删除。仍可用、待清除或活动暂存的载荷始终受保护。
- 若数据库已知 ID 或目录扫描被截断，新分享暂时失败为存储受限；后续维护分批推进，不以无界扫描阻塞启动。

### 容量与清理所有权

- 16 MiB/512 份预算现在同时统计正式生命周期与 staging 行；无大小的旧孤儿按 64 KiB 保守估算。
- 回滚必须先用 lease CAS 释放本次登记，再复查 payload 是否已被 RawEvent 接管，最后才允许删除文件。陈旧租约不得删除新请求或已提交事件的证据。
- 文件 ID 碰撞时只释放本次登记，不删除既有文件；既有文件随后只能由匹配重试、用户清除或受保护的孤儿恢复流程处理。

## 当前验证与限制

纯 Kotlin 测试覆盖活动/到期租约、容量统计、恢复中拒绝、显式回滚、清理异常不掩盖主诊断，以及陈旧租约不得删除新文件。Room instrumentation 覆盖 v4→v5 迁移、登记与 RawEvent 同事务消费、恢复 CAS、已跟踪/活动载荷保护、`CLEARED` 残留回收、孤儿目录边界，并通过关闭磁盘数据库后重新打开来验证暂存登记跨组件重建仍可恢复。

以下仍是独立发布门：

- 尚未完成真实 Android 系统强杀发生在每个 I/O 切点的矩阵、恶意/大量 Intent 压力和多进程协调；当前应用仍按单进程设计。
- 4096/512 是安全上限，不是性能结论；大量历史与异常目录仍需 TD-014 的基准。
- 本决定只关闭通用分享证据的未索引文件窗口，不增加支付宝、微信支付或银行适配器，也不证明任何 provider 格式。
- 该变更涉及数据库 schema、敏感文件删除和并发所有权，发布合并前仍需高级工程师复核迁移、API 与安全边界。

## 结果

- 正面：进程退出留下的文件可被数据库租约确定所有权并有界回收；容量统计不再只看已提交 RawEvent；活跃提交与删除之间有 CAS 边界。
- 代价：每次新分享增加至少一次 Room 登记事务，启动维护需要小批量数据库查询和目录检查。
- 风险：系统时钟大幅跳变可能让租约提前或延后到期；失败语义保持安全关闭，但可能要求用户重试。

## 被否决方案

- 只扫描目录并按文件年龄删除：无法证明文件是否仍由活动提交者拥有。
- 文件落盘后再写 journal：仍保留原来的崩溃窗口。
- 让 RawEvent 提交后异步删除 journal：会产生数据库已提交但 journal 长期占用容量的双重事实。
- 文件碰撞时直接覆盖或删除旧文件：可能销毁另一个请求或已提交事实的唯一原始证据。
- 启动时无界遍历整个目录：异常目录会让冷启动和新分享成本不可控。
