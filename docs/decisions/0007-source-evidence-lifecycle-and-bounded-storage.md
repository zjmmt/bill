# ADR-0007：来源证据生命周期与有界本地存储

- 状态：已接受；生命周期切片已实现，staging 崩溃窗口由 ADR-0008 关闭，发布级压力与系统强杀矩阵未完成
- 所有者：项目维护者
- 最后核验：2026-07-25
- 事实来源：当前 `source:review-contract`、`application`、`data:local`、Compose 设置页与 Room v4 生命周期实现；ADR-0003、ADR-0006、ADR-0008

## 背景

ADR-0006 建立了来源中立的分享文本证据主干，但原始载荷会随应用数据无限保留。只有硬配额而没有删除入口会让用户最终永久无法继续分享；只删除文件而不保留状态又会让 UI、审计和重试把已经不存在的原文误当成可用证据。来源证据因此需要同时具备用户入口、自动保留、容量治理、分页、崩溃恢复和明确的结构化记录边界。

## 决定

### 不改变 RawEvent 事实

- `RawEvent` 的来源、哈希、采集时间和 payload ID 仍然不可变。载荷是否仍存在由独立的 `source_evidence_payloads` 生命周期记录表达，不覆盖或删除 RawEvent。
- 清除原始载荷只移除应用私有文件。RawEvent、ParseAttempt、来源建议、已完成 Draft 的证据链接、审计和正式账本继续保留。
- 对仍在 `WAITING_USER` 的来源建议执行清除时，同时把建议标记为 `DISMISSED`；已经完成的 Draft 和 provenance 不受影响。

### 两阶段、可恢复清除

- 生命周期状态为 `AVAILABLE -> CLEAR_PENDING -> CLEARED`。请求阶段在单个 Room 事务内写 command receipt、请求审计、清除原因并处理待复核建议；文件删除成功后，第二个事务才标记 `CLEARED` 并写完成审计。
- 文件删除失败或进程在两个阶段之间退出时，状态保留为 `CLEAR_PENDING`。应用启动维护和用户“重试清除”都复用原 command/work，不制造第二套删除事实。
- 用户清除前必须看到不可恢复确认，且 UI 在完成后明确显示“原始内容已清除、结构化记录保留”。状态、错误和审计不得回显原文。

### 保留、容量与分页

- 新建和迁移数据库的默认保留期限为 30 天；用户可选择 7、30、90 天或永久保留。保留规则只自动处理已经没有待复核建议的证据。
- 已跟踪载荷的硬预算为 16 MiB、512 份。新分享到达前先测量旧版未知大小，并优先清除最旧、已经处理完的证据；待复核证据不会因容量自动删除。若没有安全候选，入口明确失败为存储已满。
- 旧版记录缺少大小时，只读取有界文件头核验实际 payload 大小；文件已经不存在时，以 `MISSING_PAYLOAD` 原因进入同一两阶段清除语义，不伪造内容。
- 设置页每次读取 20 项，仓储使用 `(capturedAt, rawEventId)` keyset cursor，单次上限 100；不使用随历史增长而退化的 OFFSET，也不向 UI 读取原始正文。

### Room v4 与完整性

- Room v4 新增 `source_evidence_payloads` 和单例 `source_evidence_policy`。`v3 -> v4` 正式迁移为每个现有 RawEvent 回填 `AVAILABLE` 生命周期和未知大小，并建立默认 30 天策略。
- 新 RawEvent 与生命周期记录在同一事务写入；payload ID 全局唯一。安全重放必须仍为 `AVAILABLE` 且大小不冲突，已经清除的旧 command 不得重新写回同一个 payload。
- 全局来源状态验证 RawEvent/生命周期一一对应、payload ID、状态字段、清除审计、command receipt、策略和待复核关系；损坏时失败关闭。

## 当前验证与限制

纯 Kotlin 生命周期服务测试覆盖删除失败重试、保留期限、未知大小、缺失文件、容量淘汰和“待复核不自动删除”。MuMu API 32 最终 24 个 Room instrumentation 测试覆盖 v3→v4 迁移、两阶段清除、幂等/碰撞、分页、直接恢复任意待清除工作项、待复核 dismiss、已完成 Draft/provenance 保留、文件测量/删除和损坏状态失败关闭；设置页的即时刷新、保留切换和清除确认另经手工复测。

仍有以下发布门：

- 本 ADR 原有的未索引文件窗口已由 [ADR-0008](0008-leased-source-evidence-staging-and-orphan-recovery.md) 关闭：Room v5 在文件写入前登记租约、由 RawEvent 事务消费，并有界回收旧孤儿。预算现在同时统计已提交生命周期和 staging。
- 尚无大量/恶意 Intent 压力基准、自动化 Compose 删除确认、进程死亡矩阵或真实 Samsung/小米验证。
- 当前只提供逐项原始载荷清除；“全部账本/全部本地数据”删除、加密备份及其删除语义仍未实现。
- 该能力不提升支付宝、微信支付或银行支持状态；真实适配器仍需脱敏样本、回放与真机验收。

本决定改变数据库 schema、删除语义和敏感数据保留面，合并前需要高级工程师复核迁移、API 契约与安全边界。

## 结果

- 正面：用户可以看见和控制原始证据保留；清除可重试且不会把结构化账本历史一起抹掉；自动容量治理不会牺牲待复核证据。
- 代价：每个 RawEvent 增加生命周期行、审计和完整性检查；清除不是物理删除整个事实链。
- 风险：租约与有界扫描关闭了核心 staging 崩溃窗口，但大量/恶意 Intent、真实系统强杀切点和异常目录性能仍须独立验证。

## 被否决方案

- 清除时删除 RawEvent、ParseAttempt 或已完成 Draft provenance：会破坏审计、幂等和账本解释能力。
- 直接从 `AVAILABLE` 删除文件后再补数据库状态：进程退出会让数据库继续声称原文可用。
- 容量满时删除最旧记录而不看复核状态：可能在用户判断前销毁唯一原文。
- 使用 OFFSET 分页：历史增长后扫描成本不稳定，且并发新增会造成跳项或重复。
- 只提供硬配额、不提供设置和清除入口：会把资源保护变成用户无法解除的永久锁死。
