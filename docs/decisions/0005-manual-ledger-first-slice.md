# ADR-0005：手工本地账本首片的复式记账与持久化边界

- 状态：已接受；手工切片已通过自动化/MuMu，真机验收待完成
- 所有者：项目维护者
- 最后核验：2026-07-25
- 事实来源：当前 `core:domain`、`core:ledger`、`application`、`data:local` 与 Android UI 实现；ADR-0001、ADR-0003；来源扩展见 ADR-0006

## 背景

支付宝、微信支付和银行尚无可提交的真实脱敏样本。此时伪造来源解析器会制造虚假的“已支持”结论，也无法验证通知、文件格式或跨来源去重。项目仍需要先证明账户、草稿、复式分录、Room 事务、审计和 UI 可以形成一个真实的本地闭环。

## 决定

### 手工输入与外部证据分流

用户主动输入是 `ManualIntent -> Draft`，不伪装成支付宝、微信或银行 `RawEvent`，也不创建虚假的外部来源证据。未来通知和文件仍先进入不可变 `RawEvent`，解析后再汇入同一 Draft 状态机。

### 首片账户与币种门

- 首片只接受 CNY，不进行跨币种求和，也不在缺少汇率与换汇分录时自动过账。
- 用户可创建现金、银行卡、电子钱包余额和信用卡账户；贷款、投资及渠道包装账户仍留在后续切片。
- 账户显示余额均为用户视角正数；账本内部按有符号金额计算。资产和费用增加为正，负债、收入和权益增加为负，因此信用卡欠款在账本中是负数。

### 隐藏系统账户与期初余额

首片建立三个不可由用户选择、也不进入资金账户或净资产列表的系统账户：

- `system:expense:uncategorized`：未分类费用；
- `system:income:uncategorized`：未分类收入；
- `system:equity:opening`：期初权益。

期初余额不是直接写入账户余额列，而是创建平衡的 `ADJUSTMENT` 交易。手工收入/支出先成为 Draft，选择真实资金账户后才生成平衡 Entries 并确认。

### 原子写入、幂等与撤销

- 账户创建、可选期初交易、Entries、审计记录和命令回执在同一 Room 事务内提交；草稿确认和撤销同理。
- 全局 `command_receipts` 用命令 ID、操作、目标和规范请求指纹区分安全重试与命令碰撞；回执不保存账户名、金额、备注或对手方原文。
- 指纹覆盖稳定业务意图，不纳入服务在每次调用重新生成的生命周期时间戳；否则首次提交成功但响应丢失后，同一 command ID 会被错误判成碰撞。Draft 的业务发生时间则在确认时与正式交易显式绑定。
- 撤销不删除交易或 Entries，而把交易标记为 `VOIDED`。余额查询只汇总 `ACTIVE` 交易；若交易来自 Draft，则把 Draft 恢复为 `WAITING_USER`，并追加审计记录。

### 依赖方向与迁移

- 新增纯 Kotlin `core:domain`，存放首片领域实体和 `LedgerRepository` 端口；`application` 编排用例，`data:local` 实现 Room 仓储，App 作为组装根手工连接依赖。
- Room 从 schema v1 升到 v2，新增账户、草稿、交易、分录、审计和命令回执表，并声明正式 `v1 -> v2` 自动迁移。运行时禁止 destructive fallback。

## 当前实现与验证边界

上述边界已有代码实现和导出的 Room v1/v2 schema；当前数据库已由 [ADR-0006](0006-provider-neutral-shared-text-evidence-spine.md) 与 [ADR-0007](0007-source-evidence-lifecycle-and-bounded-storage.md) 向前迁移到 v4，但没有改变本决定的手工账本语义。`code-review` 后补充的失败关闭映射、稳定指纹、Draft 发生时间绑定和真实 Room 测试，已经过完整自动化、Lint、Debug 构建与 MuMu API 32 connected instrumentation 验证。当前仍只能称“部分实现”而非发布级“已验证”，因为自动化 Compose/进程重建和真实设备矩阵尚未完成。

支付宝、微信支付和银行的通知监听、文件导入、解析器、样本回放和跨来源关联均未由本决定实现。三类来源在 UI 中必须保持 `FALLBACK_REQUIRED`，只引导用户使用当前手工回退路径。

## 结果

- 正面：在不伪造来源能力的前提下，先验证共享 Draft 与账本主干；复式余额、幂等和撤销语义从第一笔真实本地数据开始成立。
- 代价：首片只有 CNY 和四类常用资金账户，尚不能表达多币种、投资、贷款、转账、还款、退款或来源证据关系。
- 风险：迁移和仓储测试已经在 MuMu 执行，但并发压力、事务失败回滚全矩阵、进程重建和 OEM 真机行为仍需更多自动化与设备证据。

## 被否决方案

- 为手工录入创建假的 `RawEvent`：会污染证据链并模糊来源支持状态。
- 直接维护账户余额列：无法保留平衡分录、期初依据和可审计撤销。
- 删除已确认交易再重建草稿：会破坏历史、幂等和审计连续性。
- 在首片里隐式换算或合并币种：缺少汇率、费用和换汇分录，净资产会失真。
- 把隐藏损益账户暴露为付款账户：会让账务科目与用户真实持有资金混为一谈。
