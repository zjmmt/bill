# ADR-0009：电子钱包余额不得由银行卡流水反推

- 状态：已接受；领域约束已冻结，钱包 provider 采集仍待验证
- 所有者：项目维护者
- 最后核验：2026-07-25
- 事实来源：账户产品规格、对账设计、项目负责人在港版 S24 Ultra 上报告的微信通知行为、财付通公开隐私政策

## 背景

支付宝余额、微信零钱和银行卡是不同的资金账户。绑卡支付、充值和提现可能在银行侧留下记录，但余额账户内的红包、个人转账、余额消费、退款或收款可以完全不触发银行卡流水。

项目负责人报告的当前微信环境中，未领取红包通知不含金额；领取红包、发送红包和发送个人转账可能不产生通知。该报告是当前设备/账户/版本的待复核观察，不可泛化为所有微信客户端；但它足以否决“通知或银行卡流水必然补全微信零钱账本”的假设。

财付通公开隐私政策说明，微信支付一般提供交易记录查询和下载入口；公开说明不等于该入口在港版设备、特定账户、地区、版本或导出结果上都可用。因此它只能作为待实机确认的候选路径，不能提前写成已支持能力。

## 决定

1. `ASSET_EWALLET_BALANCE` 是独立资产账户。支付宝余额、微信零钱各自的收入、支出、红包、个人转账和退款，必须由其自身的可验证证据进入账本。
2. 银行证据只描述银行卡账户变化。只有在同一经济事件的资金腿被明确证实（例如充值、提现、绑卡消费）后，才可通过 `TRANSFER_PAIR`、`FUNDED_BY` 或后续明确关系关联；银行记录不得反推未知的钱包内部事件。
3. 钱包余额快照与账本运行余额的差异只创建 `ReconcileCase`。它不得自动生成收入、支出、转账、红包或调整分录。
4. 未领取红包、未接受个人转账、已退还但未曾入余额的记录不是既成资金流，不能先记收入再冲销。若未来证据确认“先入余额、后独立转回”，两次已发生资金流才由显式关系关联，不能混同为普通商户退款。
5. 通知采集只能是尽力的即时证据，不能被列作微信零钱或支付宝余额完整性来源。没有逐版本交易模板和用户明确隐私同意时，不保存混合聊天/支付 App 的通知正文。

## 结果

- 余额钱包与银行同时存在时，系统可以正确表示跨账户资金移动而不双计，也不会将钱包内收付丢失后伪造为银行卡收付。
- 对账会明确显示“钱包证据缺口”，而不是以看似平衡的假数据掩盖漏账。
- 要达到接近完整的钱包记录，后续必须验证钱包自身的用户账单路径，或另行由用户作出高风险屏幕辅助采集的产品决策；读取私有目录、Root、抓包和默认无障碍自动操作仍不在路线内。

## 被否决方案

- 以银行卡流水补齐微信零钱/支付宝余额：会遗漏余额内收付，并把充值、提现或绑卡消费错误解释为普通收入/支出。
- 对无金额或缺失通知使用金额正则、余额差或历史模式猜测：会制造不可审计的虚假交易。
- 将所有红包或个人转账默认记为收入/支出：无法表达未领取、过期、退还、代收代付和余额内往返。
- 默认启用无障碍或保存微信全部通知：权限和聊天隐私代价过高，且仍不能保证完整性。
