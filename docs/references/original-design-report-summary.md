## 采用的核心方向

- Android 原生、本地优先、离线、无自有服务器。
- 通知负责即时观察，用户账单导入负责补齐和对账，手工录入是正式回退。
- 原始事件先进入 Draft，确认后才形成 Transaction 与 Entries。
- 底层保存经济事件、会计分录和关联，而不是一张扁平流水表。
- 渠道与资金账户分离；绑卡支付不能在渠道和银行各记一次支出。
- 负债有独立状态、到期日和还款节点；还款不是第二次支出。
- 投资计入资产，但首期以导入/手工持仓为主。
- 重点测试解析回放、分录平衡、导入幂等、去重、对账、撤销和恢复。
- Android 技术基线：Kotlin/Compose、Room/SQLite、Notification Listener、WorkManager、SAF、Keystore。

## 被项目负责人明确推翻的假设

报告把产品定义为“Alipay 优先的本地记账中枢”，V1 的通知、CSV、样本、里程碑和投资均以支付宝为中心，微信和银行只预留接口。

该范围已被替换：**支付宝、微信支付和银行都是 MVP 一等数据源**。详见 [ADR-0002](../decisions/0002-three-first-class-source-families.md) 与 [来源覆盖矩阵](../product-specs/source-coverage.md)。

## 需要重新验证而非直接继承的内容

- 原报告的通知正则只是建议示例，不是官方稳定格式。
- 支付宝/微信个人账单的当前容器、编码、表头、跨度和密码流程需真机样本冻结。
- 所有银行格式和通知文案需按具体 provider 验证，不存在已证明的通用模板。
- 4–6 周工期是支付宝优先原型估计，不适用于生产级三来源 MVP。
- 去重权重/阈值必须按关系类型用标注样本校准，不能直接采用固定公式。
- Room 不等于数据库已静态加密；密钥、备份和恢复需独立威胁模型。

## 对原报告下一步清单的改写

原先“建立 50–100 条支付宝样本、先做支付宝通知和 CSV”改为：

1. 冻结 provider-neutral 枚举、来源契约和分录不变量。
2. 为支付宝、微信和首批具体银行分别建立同量级脱敏样本与格式版本。
3. 先跑通手工录入的完整纵向切片，再让三个来源并行进入相同 Draft 流程。
4. 优先验证通知/文件幂等、渠道到银行资金关系、转账、还款和退款。
5. 支持状态按来源/格式证据升级，不以预留接口充当已支持。
