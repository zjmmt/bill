# 核心设计信念

- 状态：已确认
- 所有者：项目维护者
- 最后核验：2026-07-19
- 事实来源：项目目标与 Harness Engineering 方法

## 1. 仓库是记录系统

对未来贡献者而言，未进入仓库的聊天、口头决定和外部文档等同于不存在。根 `AGENTS.md` 只给地图；产品事实、架构边界、执行计划、决策与质量证据分别进入结构化目录。

## 2. 先建立中立内核，再接来源

领域核心处理金额、账户、交易、分录和关系，不认识“支付宝交易”这种核心实体。支付宝、微信和每家银行只在适配器边界表达差异。

## 3. 原始证据不可变，派生结论可重建

通知、文件行和用户输入先形成证据；解析、分类和关联都是带版本的派生结果。规则升级时重放，而不是覆盖历史证据或用户决定。

## 4. 经济事件与观测分离

一杯咖啡可能被支付宝、微信、银行通知和账单文件多次观测，但总账只应有一个经济事件。多份观测通过关系连接，不用“删掉重复行”丢失证据。

## 5. 在边界解析，在核心强约束

外部输入不可信且会漂移。适配器可以容忍未知可选字段，但金额、币种、方向等关键事实缺失时必须安全失败。进入正式账本后必须满足平衡、幂等和审计不变量。

## 6. 不确定性是数据，不是异常羞耻

置信度、候选账户、缺失证据和冲突原因必须被建模并展示。无法确定就停在草稿，不通过复杂默认值伪装自动化。

## 7. 用户修正优先且可复用

用户对商户、分类、账户和关系的修正拥有明确优先级。系统可以据此生成本地规则建议，但不能让后续低可信导入静默覆盖。

## 8. 约束要能被机器执行

重要边界最终应落为模块依赖检查、schema 测试、黄金样本回放、分录性质测试、敏感日志检查和文档 lint。仅写“请注意”会随规模增长而失效。

## 9. 支持声明来自证据

设计目标、实验性能力和实际支持必须分开。只有真实脱敏样本、自动回归和用户回退路径都存在时，某个来源/格式才称为正式支持。

## 10. 熵需要持续清理

重复辅助函数、来源特例、过时文档、无主规则和不一致错误码会被智能体继续复制。小步、定期的文档整理和结构检查是开发流程的一部分，不等到“大重构”。
