# ExecPlan 0008：仓库边界守卫与生成事实

- 状态：进行中
- 所有者：项目维护者
- 最后核验：2026-07-31
- 事实来源：ARCHITECTURE.md 的依赖方向、SECURITY.md 的无敏感日志/最小权限边界、QUALITY_SCORE.md 与 TD-007

## 目的与用户可见结果

把目前只能靠人工记住的架构、安全和仓库事实变成可重复检查：来源适配器不能依赖 Room、Android UI 或正式账本；生产源码不能引入直接日志/控制台输出或高风险权限；Gradle 模块依赖、Room schema、源 Manifest 声明和测试源码数量由生成器维护，不再手工复制。

这组工作提高未来支付宝、微信和银行适配器接入的可信度，但不实现或声明任何 provider 支持，也不把“测试源码存在”写成“测试已经运行通过”。

## 范围

1. 建立声明式 Gradle 项目依赖允许表，校验未知模块、未知依赖、逆向依赖和循环。
2. 扫描生产 Kotlin/Java 的直接日志与控制台 API、直接遥测依赖，以及源 Manifest 中未显式移除的网络/短信/广泛存储高风险权限。
3. 生成 `docs/generated/repository-facts.md`，只记录可从源码机械提取的模块依赖、Room schema 版本、Manifest 源声明和测试源码计数，并包含输入摘要。
4. 为守卫补正反例自测，接入本地 CMD 聚合命令与 GitHub Actions push/PR 门。
5. 更新基础计划、质量评分、技术债务和生成文档索引；使用 `code-review` 复核绕过路径、误报和生成确定性。

## 非目标

- 不运行 Android 设备测试，不把测试源码数量等同于通过数量。
- 不读取真实财务数据、通知样本、构建缓存或设备状态。
- 不生成 provider 支持矩阵；真实适配器仍由脱敏样本和回放测试驱动。
- 不以正则守卫替代 Android Lint、Gradle 编译、代码审查或发布 APK 审计。

## 验收

- 当前仓库通过全部守卫。
- 合成反例能证明来源→Room、直接日志、网络权限新增和陈旧生成文档会失败。
- 生成器在输入未变时字节稳定；输入变更但未重生成时 CI 失败。
- 生成文档明确区分“源码中存在的测试”与“已执行通过的测试”。
- 所有检查都可从仓库根目录经 `cmd.exe /d /s /c scripts\check-repository.cmd` 运行。
